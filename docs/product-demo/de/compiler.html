Das Produktversprechen

Ein erfolgreicher Build bedeutet mehr als «Word öffnet die Datei».

docc behandelt einen Dokumenttyp als Vertrag: verfasstes Markdown wird geparst, die erklärten Anforderungen werden geprüft und erst dann durch das gewählte Theme gerendert.

AUF DIESER SEITEDer VertragPrüfebenenDiagnosenBefehleReproduzierbarkeit
Eine klare Grenze

Inhalt verfassen. Regeln erklären. Ergebnis kompilieren.

Eine Word-Datei kann eine fehlende Empfängeradresse, einen alten Platzhalter, eine Überschrift am falschen Ort oder einen ungültigen Rechtswert enthalten. Das sind Dokumentfehler. docc legt dieses Wissen in ein Schema, damit es einheitlich geprüft werden kann.

VERFASSTQuelleMarkdown und YAML bleiben sichtbar, prüfbar und editierbar.
ERKLÄRTSchemaDer Typ sagt, welche Angaben und Strukturen gültig sind.
GEWÄHLTThemeDas Profil legt das Rendering eines gültigen Typs fest.
ERZEUGTAusgabe.docx entsteht erst, wenn die Quelle alle Prüfungen bestanden hat.
Was docc nicht tut: Es erfindet keine Tatsachen, speichert keine Dokumente und verwandelt keine Vorlage in eine Anwendung. Die Eingabe ist ein verfasstes Dokument; das Ergebnis eine geprüfte Kompilierung.
Prüfebenen

Anforderungen werden dort geprüft, wo sie hingehören.

Das Schema bestimmt die gültige Form eines Dokumenttyps. Der Compiler vergleicht die Quelle damit und führt die Regeln des Typs aus.

EbeneFrageBeispiel
Marker und TypIst dies ein docc-Dokument und welcher Vertrag gilt?docc: 1 und document_type: ch_letter wählen einen bekannten Typ.
Frontmatter-SchemaSind Pflichtwerte vorhanden, typisiert und korrekt formatiert?Eine Postleitzahl hat vier Ziffern; ein Enum nutzt einen erlaubten Wert.
TextstrukturSind verlangte Überschriften in erwarteter Reihenfolge vorhanden?Eine Rechtsschrift kann feste Hauptabschnitte verlangen.
SemantikSind Blöcke, Spans und bewusste Leerfelder richtig verwendet?Ein Parteienblock kann Name, Geburtsdatum und Adresse verlangen.
RegelnGelten dokumentübergreifende Vorgaben?Eine Platzhalterregel verhindert [Name] in der Ausgabe.
Schema/ThemeKann das Theme die Erklärung tatsächlich rendern?Ein fehlender Stil wird vor dem ersten Absatz zurückgewiesen.

Der Compiler sammelt alle Befunde in einem Durchlauf. Niemand soll nach jeder Korrektur nur den nächsten überraschenden Fehler sehen.

Nützliche Fehler

Jeder Fehler zeigt Ort und nächste Handlung.

Diagnosen besitzen stabilen Code, Quellposition und Hinweis. Damit funktionieren dieselben Ergebnisse im Terminal, im Editor, in CI oder in einem automatisierten Entwurfsablauf.

brief.md:8:13: error[DOC010]: Feld `case_ref`
hat ungültigen Wert "ZG2026000"
  |
8 |   case_ref: "ZG2026000"
  |             ^^^^^^^^^^ Format AA.YYYY.NNN,
  |                        z. B. "ZG.2026.000"

Stabiler Code. Ein Workflow erkennt die Fehlerklasse, ohne Meldungstext zu erraten.

Cursor in der Quelle. Korrigiert wird die Markdown-Datei, nicht die generierte Word-Datei.

Handlungsfähiger Hinweis. Das erwartete Format steht beim Fehler, nicht nur in einer mündlichen Regel.

Den Compiler nutzen

Ein Vertrag, mehrere sinnvolle Ansichten.

# Ohne Ausgabe validieren.
docc check brief.md

# Validieren und danach Word erzeugen.
docc build brief.md

# Vertrag und Diagnosen für Tools oder CI.
docc describe --json ch_letter
docc check --json brief.md

# Geparste Tatsachen und Struktur als JSON lesen.
docc read brief.md

docc lsp

check --json liefert ok, Fehler- und Warnungszahlen sowie Diagnosen als strukturiertes JSON. So muss kein anderes Tool menschliche Terminalausgabe parsen.

Wiederholbares Ergebnis

Gleiche Eingaben, gleiche Dokument-Bytes.

docc schreibt das .docx selbst. Bei unveränderter Quelle, Schema und Theme ist das Archiv auf jeder Maschine byte-identisch. Das Dokument enthält die Profil-Provenienz; Uhrzeit, Netzwerk und sonstiger Umgebungszustand gehören nicht zur Ausgabe.

Für einen Brief bedeutet das: Ein neuer Build ist nicht nur «wahrscheinlich gleich». Wenn sich die Bytes ändern, hat sich eine Quelle oder ein Profilinput verändert.

Das verbindliche Modell beschreibt die Philosophie.
