The daily loop

One source, one feedback loop.

Discover. Start with types, describe and example. They make the document contract visible before you draft.

Author. Edit Markdown and frontmatter. Keep facts as data and prose as prose.

Check. Run docc check during drafting or let the LSP surface the same diagnostics in the editor.

Build. Render only the passing source. The profile supplies the fixed look; the compiler supplies the proof that the declared requirements passed.

Review inputs. Treat a changed source, schema, theme or profile lockfile as a real document change. Rebuilds are deterministic.

# A minimal, explicit CI check.
docc check --strict docs/*.md

# A machine-readable variant for another tool.
docc check --json docs/*.md

A useful diagnostic path

When a document does not build, start with the source line.

Read the error code, caret and hint. Correct the authored file first. If the reported issue is about a type requirement, inspect docc describe <type>. If it is about what profile or theme is active, use docc doctor or docc profile status.

docc check brief.md
# Correct source facts or structure from the diagnostics.

docc describe ch_letter
# Revisit the type contract.

docc doctor
# Verify the schema and theme selection.
Do not repair the generated Word file as the primary source. The Markdown file is the input the compiler can verify and rebuild. A manual output patch cannot become part of that contract.
